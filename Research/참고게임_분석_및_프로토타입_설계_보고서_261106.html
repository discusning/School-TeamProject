한눈에 보기

· 참고 게임 2개(Papers, Please / That's Not My Neighbor)의 공통 뼈대는 "방문자 → 서류 대조 → 판정 3택 → 결과"다.

· 프로토타입 필수 메커니즘은 4개: 검문 루프, 서류–주민 DB 대조, 외부인 판별, 판정+결과 피드백.

· 개발 환경은 Unity 6.5 (6000.5.9f1) + URP 2D로 확정, 저장소에 프로젝트 생성 완료.

· 임시 UI는 "위: 방문자 부스 / 아래: 서류 탭 + DB 단말기 + 판정 버튼" 배치를 추천 (비슷한 게임 20개 조사 기반).

· 팀 확인 필요: 판정 버튼 수, 시간 제한, DB 표현 방식, 검역 소견서 항목.

3. 메인 메커니즘 후보 6개

① 서류–DB 대조 (가장 핵심)

  • 페이퍼 플리즈: 검사 모드에서 두 항목을 고르면 게임이 일치·불일치를 알려준다.
  • 실수 판정이 공정해지고, 1인 개발로도 구현이 쉽다.
  • 우리 게임: "서류 항목 ↔ 주민등록 DB 항목" 클릭 대조로 그대로 옮길 수 있다.

② 날짜별 규칙 추가 (난이도 곡선)

  • 페이퍼 플리즈: 1일차 "외국인 입국 금지"로 시작해 3·4·6·8·13·21·26·27일차마다 서류·규칙이 늘어난다.
  • 하루 실제 시간도 3분 → 8분으로 늘어난다.
  • 우리 게임: 1일차 DB 대조만 → 외형 → 범죄 이력 → 검역 소견서 → 이동 시간 순으로 하나씩 연다.
  • 시스템 수를 늘리지 않고 볼륨을 만든다. (개발 범위 가이드 "볼륨은 콘텐츠로")

③ 외형 판별

  • That's Not My Neighbor: 서류는 완벽한데 외형이 미묘하게 다른 경우가 공포 포인트다.
  • 우리 게임의 "사람으로 완벽히 변신한 외부인"과 가장 가깝다.
  • 아트 인원 2명이 외형 변형 그림으로 볼륨을 채우기 좋다.

④ 판정 3택 + 신고의 무게

  • That's Not My Neighbor: 사람을 잘못 신고하면 그 주민이 죽는다. 도플갱어를 들이면 밤에 주민이 죽고 다음 날 명단에서 사라진다.
  • "거부보다 신고가 무거운" 구조가 긴장감을 만든다.
  • 우리 게임: 신고 대상이 정부에 끌려가는 식으로 디스토피아 설정과 연결할 수 있다.

⑤ 실수 페널티와 생계

  • 페이퍼 플리즈: 급여 1명당 5크레딧, 경고장은 하루 2번까지 봐주고 3번째부터 벌금. 번 돈으로 집세·식비·난방비·약값을 내고, 못 내면 가족이 아프고 죽는다.
  • That's Not My Neighbor: 돈·시간 제한 없음. 대신 S~F 등급.
  • 우리 게임: "돈이 의미 없는 세계"이므로 크레딧 대신 물자 배급으로 바꾸면 같은 구조가 된다. 1차 회의 노단비 아이디어(물자 미지급·가족 굶주림)와 맞물린다.

⑥ 스토리 NPC + 일반 방문자 섞기

  • 페이퍼 플리즈: 대본 인물(EZIC 요원, 뇌물 주는 사람)과 랜덤 입국자를 섞고, 대하는 방식에 따라 엔딩 20개로 갈린다.
  • 우리 게임의 "메인 NPC 6명 + 일반 검문 대상" 구조와 같은 방식이다.

5. 추가 참고: 개발자 일지와 새 참고 게임

페이퍼 플리즈 개발자 일지 (루카스 포프, 2012~2013)

  • 첫 프로토타입은 며칠 만에 만들었다. 서류 끌기, 규정집, 하드코딩된 입국자 1명뿐. 허가·거부 도장도 없었다.
  • 그 1명에게 오류 4개를 심어 공개하고 "다 찾아보라"고 해서 반응을 봤다.
  • 모든 오류는 "두 정보가 서로 맞지 않음"으로 통일했다. 그래서 검사 모드 하나로 어떤 오류든 지적할 수 있다.
  • 정보 쌍이 약 600개라 전부 대조하긴 어렵고, 눈으로 훑다가 의심 가는 곳을 찍게 된다.
  • 입국자 상당수는 오류가 없어야 한다. 전원이 수상하면 긴장감이 사라진다.
  • 스토리 인물도 일부 속성만 정하고 나머지(얼굴·국적·오류)는 매번 랜덤으로 채웠다.
  • 도장은 버튼을 누르는 순간 "쿵" 소리와 함께 찍히게 했다. 손맛을 중요하게 봤다.
  • 하루 끝 통계 화면은 빼고 편지·질책 같은 이야기로 결과를 전했다.
  • 테스터 피드백으로 경고장에 "무엇을 틀렸는지" 정확히 적도록 바꿨다.

Quarantine Zone: The Last Check (2026년 1월 출시)

  • 좀비 사태 검문소에서 생존자를 검사하는 게임.
  • 체온·맥박계, 반사 망치, 청진기 같은 도구로 증상을 하나씩 확인한다.
  • 날이 갈수록 도구·증상이 열리고, 뻔한 징후만으로는 판별이 안 되게 어려워진다.
  • 우리 게임의 "검역 소견서"와 가장 가까운 사례.
  • 단점: "도구 조작이 번거롭다", "후반에 반복적"이라는 평. 우리가 피해야 할 점.

항목결정이유

7. 프로토타입 필수 메커니즘

1차 회의록에서 채택·가능으로 판정한 검문 파트만 추렸다. 개발 범위 가이드의 "핵심 시스템 3~4개"에 맞춘다.

#메커니즘프로토타입 범위
1검문 루프 (뼈대)방문자 등장 → 서류 제출 → 판정 → 다음 방문자. 하루 5~9명.
2서류–주민등록 DB 대조생년월일·주소부터. 도장·서명, 범죄 이력은 데이터만 추가하면 붙음.
3외부인 판별외형 + 검역 소견서. 이동 시간은 지역 거리표가 필요해 뒤로 미룸.
4판정 + 결과 피드백통과·거부 버튼, 맞음·틀림 표시, 하루 정산. QA 테스트 기준이 됨.

8. 프로토타입 설계안

설계 원칙

  1. 판정 기준은 한 곳에서만 계산한다. 방문자를 만들 때 정답도 같이 계산해 두면 채점·QA가 쉽다.
  2. 하루 구성은 데이터로 둔다. 방문자 수·켜진 규칙·오류 비율을 날짜별 데이터(ScriptableObject)에 넣는다. 기획 팀원이 코드 없이 숫자를 바꿀 수 있다.
  3. 로직과 화면을 분리한다. 생성·판정 로직은 화면 없이 테스트할 수 있게 만든다.

데이터 구조

데이터내용
주민등록 DB주민번호, 이름, 생년월일, 주소(구역), 외형 ID, 범죄 이력
의료 기록 DB검역 소견서 대조용 (기획서: 멸망 전 서버 일부 복구) — P3에서 추가
임시 통행증1차 선별소 발급. DB 항목 복사본 + 발급일, 선별소 도장·담당자 서명
방사능/바이러스 검역 소견서선별소 발급. 검사일, 결과, 도장

방문자서류 묶음, 외형, 외부인 여부, 심어진 오류, 정답 판정

방문자 생성 방식 (페이퍼 플리즈 방식)

  1. DB에서 주민 1명을 뽑아 서류를 정확히 복사한다.
  2. 일정 확률로 오류를 하나 심는다.
  3. 오류 종류: 생년월일 불일치 · 주소 불일치 · 주민번호 한 자리 다름 · 위조 도장 · DB에 없음 · 범죄 이력 · 외형 이상(외부인) · 검역 소견서 누락·만료

화면 구성 (임시 그림)

  • 위쪽: 방문자 얼굴 + 말풍선 (1차 회의 "반반 화면" 안).
  • 아래쪽: 서류 책상 + 주민 DB 단말기. 2050년 배경이라 단말기 화면이 설정과 맞다.
  • 조작: 처음엔 클릭만. 끌어서 옮기기는 나중에.

단계별 작업 순서

단계내용확인 방법
P0데이터 구조, 방문자 생성, 정답 계산화면 없이 자동 테스트
P1검문 루프: 방문자 → 서류 → 통과·거부 → 맞음·틀림직접 플레이
P2서류–DB 대조: 두 항목 클릭 → 일치·불일치오류 심은 방문자로 확인
P3외부인 판별: 외형 변형 1종, 검역 소견서외형만 다른 방문자 섞기
P4하루 정산, 2일차 규칙 1개 추가1일차 → 2일차 이어 플레이

· P1만 끝나도 QA 팀원에게 "어떤 오류든 찾아보라"는 테스트 빌드를 줄 수 있다. (포프 방식)

9. 임시 UI 구현 방안

디자인 시안이 나오기 전까지 쓸 임시 UI 방안이다. 비슷한 게임 20개의 UI를 조사해 장단점을 나누고, 우리 프로토타입에 가져올 것과 피할 것을 정리했다.

9-2. 조사에서 나온 공통 교훈

  1. 클릭 대상은 크게, 판정까지 클릭 수는 적게. 가장 많이 나온 불만은 Beholder, Death and Taxes, Contraband Police의 "번거롭다"는 평이다.
  2. 책상이 어수선해지지 않게. That's Not My Neighbor와 Papers, Please는 서류를 자유롭게 끌어 놓다 보니 겹치고 쌓였다. 프로토타입은 서류를 정해진 자리(탭)에 펼친다.
  3. 판정 버튼은 색으로 바로 구분. Headliner처럼 통과는 초록, 거부는 빨강으로 하고 손맛 있는 효과음을 붙인다.
  4. 틀리면 이유를 바로 알려준다. 포프가 테스터 피드백으로 바꾼 부분이다. QA 테스트 기준이 된다.
  5. 외형 차이는 분명하게. Not Tonight는 픽셀 사진 구별이 어렵다는 평을 받았다. 임시 그림이라도 차이가 확실히 보여야 한다.
  6. UI 제약은 세계관으로 설명. Her Story처럼 "일부만 복구된 DB"라서 검색이 느리고 제한된다고 하면 UI 한계가 곧 설정이 된다.

9-3. 배치안 3개 비교

안배치장점단점판단
A. 부스+책상 (추천)위: 방문자·말풍선 / 아래: 서류 탭 + DB 단말기 + 도장1차 회의 "반반 화면" 안과 같음. 검문 4개 메커니즘이 한 화면에 다 보임말풍선 공간이 좁아 긴 대사엔 불리채택
B. 비주얼노벨형방문자 그림이 화면 대부분, 서류는 팝업으로 겹쳐 띄움대사·스토리 장면에 강함서류–DB 대조 시 창을 계속 열고 닫아야 함스토리 장면용
C. 단말기 전체 화면Orwell처럼 화면 전체가 정부 시스템 OS2050년 통제 사회 분위기가 강함방문자 얼굴(외형 판별)이 작아짐보류

· 검문은 A안, NPC 대사·스토리 장면은 B안으로 화면을 전환하면 1차 회의의 김도경 질문(검문 → 스토리 화면 전환)에도 답이 된다.

9-4. 임시 화면 와이어프레임 (A안)

※ 회색 상자·도형은 임시 그림이다. 디자인 시안이 나오면 같은 자리에 그림만 바꿔 끼운다.

9-5. 조작 흐름 (방문자 1명 기준)

  1. 방문자 등장 → 말풍선 대사 → 서류가 책상 탭에 자동으로 놓인다.
  2. DB 단말기에 주민번호가 자동 입력되고 기록이 뜬다. (프로토타입은 자동, 나중에 직접 입력 검토)
  3. 검사 모드(Space 또는 버튼)를 켜고 서류 칸 하나 → DB 칸 하나를 클릭 → "일치 / 불일치 / 관련 없음"이 표시된다.
  4. 통과·거부 버튼을 누르면 도장 소리와 함께 판정되고, 위쪽에 결과와 이유가 뜬다.
  5. 문제없는 방문자는 클릭 3번(탭 확인 → 통과 → 다음) 안에 끝나는 것을 목표로 한다.

9-6. Unity 구현 방법

항목방법
UI 시스템uGUI (Canvas). Screen Space – Overlay, 기준 해상도 1920×1080, 너비·높이 0.5 비율로 맞춤
화면 묶음 (프리팹)방문자 부스 · 서류 탭 · DB 단말기 · 판정 버튼 · 결과 알림 — 5개로 나눠 디자인 시안이 오면 하나씩 교체
대조 항목서류 칸과 DB 칸에 같은 "항목 종류(생년월일·주소 등)"를 붙여, 두 칸을 고르면 종류가 같을 때만 비교
한글 글꼴TextMeshPro + 무료 한글 글꼴(Noto Sans KR 등)로 글꼴 에셋 생성. 정식 글꼴은 디자인 결정 후 교체
임시 그림단색 상자 + 기본 도형. 외형 변형은 색·도형을 확실히 다르게 (예: 눈 위치·목 길이)
효과음도장 "쿵", 오답 경고음 정도만 무료 효과음으로
